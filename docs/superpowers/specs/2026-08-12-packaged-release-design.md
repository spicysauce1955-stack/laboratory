# Packaged releases: the lab as an installable tool + scaffold

**Date:** 2026-08-12
**Status:** approved design, not yet implemented
**Supersedes in practice:** the "work inside the laboratory repo" model assumed by `README.md`,
`.claude/skills/laboratory/SKILL.md`, and `deploy/scheduler/`.

## 1. Problem

Researchers use the lab by working *inside* this repo: their experiment code lives in
`experiments/`, their results in `runs/`, their MCP server is `uv run python -m lab.mcp_server`
resolved from this checkout, and the `laboratory` skill tells the agent it is operating "in this
repo". Provenance (`repo_root()`) therefore pins *lab* commits, and every change to the lab
lands directly in the researcher's working tree.

That couples two things that should version independently: the **tool** and the **research**.
There is no version a researcher can sit on while the tool advances, and no boundary saying which
parts of the tool are safe to depend on.

## 2. Goal

Each tagged version of this repo builds into an installable package that carries the CLI, the MCP
server, and the skill. Researchers install a pinned version into **their own** project repo and
scaffold it with one command. Between tags, this repo is free to change arbitrarily as long as
the declared public surface holds at the tag.

## 3. Decisions

| Question | Decision |
|---|---|
| Consumption model | `laboratory` is a **dependency of the researcher's own project**. Their repo owns experiment code, config, `runs/`, `.env`, and the git history that provenance pins. |
| Distribution | **Git tag + GitHub Release** on this (public) repo. `uv add "laboratory @ git+https://github.com/spicysauce1955-stack/laboratory@vX.Y.Z"`. No PyPI, no private index. |
| MCP + skill delivery | **`lab init` scaffolds them** into the researcher's project from data files shipped in the wheel. No Claude Code plugin/marketplace. |
| Researcher content in this repo | **Extracted** to a new `tempotron-capacity` repo. This repo keeps one example entrypoint for tests and docs. |
| Release machinery | **Both**: a local `scripts/release.sh` for the human step, GitHub Actions to verify and publish on the tag. |
| Public surface | CLI (commands/flags/exit codes), MCP (tool names/schemas), Experiment Contract, manifest + `runs/` on-disk layout. Everything else churns freely. |
| Version policy | Stay on 0.x. PATCH never breaks the surface; MINOR may, with a `BREAKING` CHANGELOG entry and an upgrade note. |

The repo being public is load-bearing: the **remote box** runs `uv sync --frozen` against the
project's lockfile, so the git dependency must resolve there with no credentials.

## 4. What a release is

A tag `vX.Y.Z` plus a GitHub Release carrying:

- `laboratory-X.Y.Z-py3-none-any.whl` and the sdist (built by `uv build`, hatchling);
- the CHANGELOG section for that version as the release notes.

The tag itself is the install ref; the attached wheel exists for offline/air-gapped installs and
as a record of what was built.

## 5. The researcher's project

```bash
uv init tempotron-capacity && cd tempotron-capacity && git init
uv add "laboratory[skypilot,gcp,r2] @ git+https://github.com/spicysauce1955-stack/laboratory@v0.5.0"
uv run lab init
```

The resulting project, with `+` marking what `lab init` contributes (`pyproject.toml` and
`uv.lock` come from uv and are never touched by `lab init`):

```
  pyproject.toml         # from uv init/add
  uv.lock                # committed; the remote runs `uv sync --frozen` against it
+ .mcp.json              # {"mcpServers":{"lab":{"command":"uv","args":["run","lab","mcp"]}}}
+ .claude/skills/laboratory/SKILL.md + examples/
+ .env.example           # machine-local settings, placeholders only
+ .gitignore             # += runs/, .env
+ .skyignore             # explicit: SkyPilot's exclusion is if/else — git-ignored != unsynced
+ experiments/example.py # a contract-honouring entrypoint (log_metric + get_overrides)
+ .lab-scaffold.json     # committed: version + content hashes, so re-runs know what it owns
```

### 5.1 Idempotence and ownership

Every generated file carries a first-line marker: `generated by lab vX.Y.Z — re-run 'lab init' to
refresh`. On re-run:

- file missing → write it;
- file present, unmodified since generation (content hash matches the one recorded in
  `.lab-scaffold.json`) → overwrite with the current version's content;
- file present and modified → write `<name>.new` beside it, warn on stderr, leave the original.

`.mcp.json` and `.gitignore`/`.skyignore` are *merged*, not overwritten: `lab init` adds its
entries if absent and leaves everything else alone. It never touches `pyproject.toml`.

`lab init --check` exits non-zero if any scaffolded file is missing or stale, so a project can
assert in CI that it has been initialised for the installed version.

## 6. Changes to the lab

`src/lab` already has no `__file__`-relative repo assumptions — `repo_root()` resolves from
`LAB_REPO_DIR` or cwd, and the SkyPilot backend syncs `Path.cwd()`. The decoupling is therefore
small:

1. **`lab init`** — new `src/lab/init.py`, with the scaffold content as package data under
   `src/lab/_scaffold/` (added to the hatchling wheel target). Also `lab init --check`.
2. **`lab mcp`** — a subcommand that runs the FastMCP server, so scaffolded configs depend on the
   console script rather than the `lab.mcp_server` module path. `python -m lab.mcp_server` keeps
   working.
3. **`lab --version`** — prints `lab.__version__` (already derived from installed metadata).
4. **`manifest.lab_version`** — recorded at `JobStore.create` from `lab.__version__`; surfaced in
   `lab status` and included in `lab export` bundles. Optional with a `None` default so existing
   manifests still parse (read-compatibility is part of the public surface).
5. **Skill relocation** — `.claude/skills/laboratory/` moves to
   `src/lab/_scaffold/skills/laboratory/` and its text is rewritten: "from inside the `laboratory`
   repo" → "in your project"; `uv run lab …` examples stay valid, `python -m lab.mcp_server`
   becomes `lab mcp`. Single source; the wheel ships it.
6. **Docs** — `README.md` rewritten around install → `lab init` → submit.
   `docs/guides/getting-started.md` for the researcher path. `deploy/scheduler/README.md` updated
   per §8.3.

### 6.1 The anti-recoupling test

`tests/test_packaging.py` (slow-marked, run in CI and by `release.sh`):

1. `uv build` into a tmpdir;
2. create a venv there and install the wheel (no editable install, no repo on `sys.path`);
3. `git init` a fresh tmp project, run `lab init` in it;
4. `lab submit -c "python experiments/example.py" --backend local` and `lab wait`;
5. assert the job succeeded, `runs/<id>/manifest.json` exists, and `lab_version` matches the
   built version.

This is the regression guard. Any future assumption that the lab lives beside the experiment
fails here rather than in a researcher's terminal.

## 7. Release process

**Version source of truth:** `pyproject.toml [project].version`. `__version__` derives from
installed metadata; nothing else restates it.

**`scripts/release.sh vX.Y.Z`:**

1. refuse unless on `main`, work tree clean, and in sync with `origin/main`;
2. gates: `uv run ruff check`, `uv run mypy --strict`, `uv run pytest` including the packaging
   smoke;
3. bump `pyproject.toml` version, `uv lock`;
4. move `CHANGELOG.md`'s *Unreleased* content into a `## vX.Y.Z — YYYY-MM-DD` section;
5. commit `chore(release): vX.Y.Z`, create the **annotated** tag with that CHANGELOG section as
   the message (matching the existing v0.1.0–v0.4.0 tag style);
6. push `main` and the tag. CI takes over.

**`.github/workflows/ci.yml`** — on PRs and pushes to `main`: `uv sync`, ruff, `mypy --strict`,
`pytest`. Cloud-credentialled tests must remain skip-without-creds; CI provides no cloud secrets.
This job is what makes "change the repo freely between versions" safe.

**`.github/workflows/release.yml`** — on `v*` tags: the same gates, then assert the tag name
equals the `pyproject.toml` version, `uv build`, and `gh release create` with the CHANGELOG
section as notes and `dist/*` attached. Failing gates mean no Release is created.

**`CHANGELOG.md`** — Keep-a-Changelog style, seeded retroactively for v0.1.0–v0.4.0 from the
existing annotated tag messages.

## 8. Compatibility contract

`docs/COMPATIBILITY.md` states it once:

**Frozen at a release** (breaking only on a MINOR bump, with a `BREAKING` CHANGELOG entry and an
upgrade note in that entry):

- `lab` CLI: command names, flag names and semantics, documented exit codes (including `wait`'s
  3 and 4, `reconcile`'s 4);
- MCP: tool names, argument names, and the shape of returned JSON;
- the Experiment Contract: `$LAB_RUN_ID`/`$LAB_RUN_DIR`/`$LAB_SEED`, `log_metric(name, value,
  step)`, `effective_config.json`, non-zero exit on failure;
- the on-disk layout of `runs/<job_id>/` and the manifest schema — and a newer lab always **reads**
  manifests written by an older one.

**Free to churn at any time:** everything under `lab.*` that is not the above (module layout,
internal function signatures, `lab.core.Lab`'s Python API), the test suite, `research/`,
`docs/`, the field reports, and the repo's own `.claude/` and `experiments/`.

## 9. Migration

### 9.1 Extract `tempotron-capacity`

Created *with* v0.5.0 (`uv add …@v0.5.0` + `lab init`), then these move out of this repo:
`experiments/`, `analyze_clean.py`, `analyze_formtest.py`, `collect_v10.py`, `run_*.sh`,
`*_done.json`, `resubmit_jobs.txt`, and the `runs/` tree (copied, since it is git-ignored).

**Fresh `git init`; no history rewrite.** Pre-split manifests pin commits in *this* repo, which
stays public with its history intact, so `lab confirm` on an old run still works from a laboratory
checkout. `tempotron-capacity/PROVENANCE.md` says exactly that rather than implying the history
moved.

This repo afterwards keeps `src/lab`, `tests`, `docs`, `research`, `LAB-REQUIREMENTS.md`, the
field reports, `deploy/`, and a single example entrypoint used by tests and the packaging smoke.
Its `.claude/skills/laboratory/` is deleted (the text lives in `_scaffold/`); its `.mcp.json`
stays, updated to `uv run lab mcp`, for dogfooding.

### 9.2 Old runs

Untouched. Read-compatibility (§8) means a v0.5.x lab reads a v0.4.0 manifest; `lab_version` is
absent on those and displays as unknown.

### 9.3 Scheduler droplet

Cuts over **last**, after v0.5.0 exists and `tempotron-capacity` is populated:

1. drain the queue — `lab queue list` must be empty. The queue dir and `runs/` are repo-rooted,
   so pending registrations under `/opt/laboratory` would otherwise be stranded;
2. `uv tool install "laboratory[skypilot,gcp,r2] @ git+…@v0.5.0"`;
3. clone `tempotron-capacity` to `/opt/tempotron-capacity`, place `.env` there;
4. unit becomes `WorkingDirectory=/opt/tempotron-capacity`,
   `Environment=LAB_REPO_DIR=/opt/tempotron-capacity`, `ExecStart=… lab scheduler tick --backend
   skypilot`;
5. verify with one cheap registered job end-to-end.

Subsequent upgrades are `uv tool upgrade` to a new tag — which is the point of the exercise.

`deploy/scheduler/` and its README are updated to describe this installed-tool deployment.

## 11. Out of scope

PyPI publication; a Claude Code plugin/marketplace; a 1.0 semver commitment; rewriting git history
to move the experiment work; multi-project or multi-tenant scheduler support.
